\## SSH 认证 50 秒原因：问题出在 PAM 会话阶段，与密码无关

**证据链**（`/var/log/auth.log`，每次 `sudo`、`ssh` 都出现同样的节奏）：

| 时间 | 事件 |
|---|---|
| 16:31:49 | 密码校验成功（`pam_deepin_authentication: 验证成功`） |
| 16:32:14 | `dbus-daemon[652]: Failed to activate service 'org.freedesktop.systemd1': timed out (service_start_timeout=25000ms)` |
| 16:32:14 | `pam_unix(sudo:session): session opened` |

即：**认证本身是瞬间完成的；之后 PAM 建立 session 时，dbus 去激活 `org.freedesktop.systemd1`，每次都会等满 25 秒，连续两次，所以约 50 秒**。SSH 用公钥登录也一样慢，证明与密码、密钥无关。

远端进一步确认了根因：

- `dbus-send --system --dest=org.freedesktop.systemd1 ... Ping` → 超时；`systemctl is-system-running` → 超时；`org.freedesktop.login1` 却能立即响应。
- `systemd-journald` 反复报 `Failed to send WATCHDOG=1 notification message: Transport endpoint is not connected`。
- 多个进程处于不可中断 D 状态：`startdde`（`mm_access`）、两个 `ThreadPoolSingleton`（`call_proc_get_link`）、`uosste-worker`；`dmesg` 显示 `display-frozen: 1`、`coretask-stall: 30`，负载约 5。
- 结论：**测试机的 systemd/PID1 与 dbus 会话链路有故障，且存在内核态卡死**，并非 sshd 配置问题。

**规避办法**：使用 SSH ControlMaster 复用连接。首次连接仍付一次 50 秒，之后所有命令（含 rsync、远端执行）走复用通道约 **0.03 秒**：

```bash
ssh -M -N -f -o ControlPath=/tmp/ypc_ssh.sock uostest@10.20.33.93
ssh -o ControlPath=/tmp/ypc_ssh.sock uostest@10.20.33.93 '命令'
```

**根治**：重启测试机（清理 D 状态进程、恢复 systemd）。这属于破坏性操作，需要你确认后我再执行；当前已用复用通道绕开 50 秒问题继续部署。
