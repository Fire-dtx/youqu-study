四个成本结论

① 主力是 flash 级模型。任务多为「读日志 → 定位 → 改一个文件 → 跑一条用例」，吞吐与工具调用稳定性比单次推理深度更重要。

② 任务形态决定模型。短任务海量并行、长会话重工具链、单轮强规程、一次读 40k 行源码，四种形态四种选型。

③ 缓存复用率是成本分水岭。建设期 6.4%，过检 95.7%，无人值守 96.2%。

④ 模型切换有成本。跨模型丢上下文风格；统一主力后文档与台账格式才稳定。

无人值守 212 个会话全部单轮、同一模型、同一规程，缓存读到 96.2% —— 这正是「强规程 + 短会话」的成本红利。

反例：并行省了人，但没省 token

461 个会话同日并行、每个 issue 独立冷启动，输入 5.3 亿 tokens、缓存读只占 6.4%。把公共上下文（版本规则、命名规范、环境说明）前置到任务模板，才能同时省轮次与输入。

最贵的一条教训：网络类用例自伤

2005719 移走 NetworkManager 并重启，用例 PASS、回退返回 True，但测试机 04:12 起 IPv4 失联 → 后续 44 条阻断、21 条误判。破坏网络的用例禁止跑在受控 SSH 通道上；用 netns/veth/独立网段，执行前后各做一次连通性断言；断链先暂停定时任务再排障。

09 / 经验可取之处

换模型不如换信息结构

最有效的改进不是更强的模型，而是把「版本/环境/入口/命名」变成清单字段、把「能不能开工」变成显式检查、把「通过」变成可取证的行为。

CONSTRAINT 01

单入口串行

只用 manage.py run；远端 flock、owner 心跳、拿不到锁 BUSY 即退、残留检查、报告裁剪。

361 条 8.5h 串行 · 并发覆盖消失
CONSTRAINT 02

行为取证

产品日志 / D-Bus / 系统状态三方取证；AT-SPI 只证明「操作发出」，不证明「行为发生」。有界重试 + 提前退出。

15 条失败 100% 有证据 · 假绿被拦
CONSTRAINT 03

台账分账

pass / fail / blocked / skipped 四分；环境故障不写 fail；record 只追加；数字从 ledger.json 可复算。

21 条误判归零的设计前提
CONSTRAINT 04

环境前提编码

源隔离、能力探测、构建校验、polkit 双后端、.venv 自举；构建失败直接报错，不静默回退旧版。

V20/V25 一套脚本 · 39 个 .so 冲突消失

12 条硬约束速查

01能力探测优于版本判断 02构建失败不静默回退 03PASS 不是证据 04有界重试 + 提前退出 05四段闭环，finally 是硬约束 06负面状态自己构造 07单一事实源：登记表 08单入口串行 09证据链即交付物 10文档是 AI 的接口 11环境故障与用例失败分账 12调度器也是被测对象

建设期：瓶颈是「信息是否足够开工」

385/466 会话出现版本歧义、77 个 blocked。版本、环境、入口、命名四件事只要一件含糊，N 个 Agent 就产生 N 次阻塞。把这些变成清单字段与任务模板，比换更强的模型有效得多。

过检期：瓶颈是「环境状态机」

测试机在线、代码已同步、锁未过期、凭据有效——四者任一不成立，产出就是噪声。所以先做「开工四问」，再谈重试。

框架：选型不是选库，是做可诊断的封装

+222 行查找日志 / −285 行默认行为；一行日志回答「元素名错 / 页面没到 / 匿名控件 / 近似名」。代价是约 500 行与上游漂移，需手工 rebase。

边界：人给边界，不等于必然通过
