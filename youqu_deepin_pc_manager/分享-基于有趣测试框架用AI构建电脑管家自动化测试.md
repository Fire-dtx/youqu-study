# 基于「有趣」测试框架用 AI 构建电脑管家自动化测试用例

> **以「变更 × 收益对比」为主线的复盘**｜2026-11-18（会话归档更新至 10:37）
> 数据来源：三套本机会话存档——内部 issue 平台的 466 个建设期会话（2026-09-28 → 2026-10-26）、本机 coding agent 的 64 个过检会话（33 个顶层 + 31 个子代理/分片，2026-09-09 → 2026-11-18，全量 JSONL 归档见 `.omp-sessions/`）、DeepSeek Harness 的 212 个无人值守过检会话（2026-11-10 → 2026-11-11），以及仓库 `youqu_deepin_pc_manager`、`youqu-ai` 当前代码/文档与 2026-11-18 V20 最终全量报告（`report_2026_1018`）。
> 会话明细见本机三套存档：建设期 issue 平台导出、过检期 `.omp-sessions/`（含子代理/分片）与无人值守 harness 会话目录（均为内部资料，不外发）。

### 0.3 一句话方案

> **变更的实质不是"让 AI 生成用例"，而是把"用例建设 + 过检"改造成三条可审计生产线，并用四条工程约束（单入口串行、行为取证、台账分账、环境前提编码）保证产出可信**：建设期用 issue 分片 + 多 Agent 并行把 12 条入口扩到 268 条资产；过检期用交互会话改规程/做归因 + 单条 worker 真机取证，把 229 条推进到全部结案；无人值守批次用定时唤醒 + 监控接管兜底调度。三者共享同一套事实源、门禁与证据链。

### 1.3 收益口径（三条硬规则）

1. **有旧基线才叫收益。** "229 条全部结案"本身不是收益，收益是"结案率 100% + 人工只介入 84 条"。没有旧行为的项（如首次建立台账）只描述"消除了哪种失败模式"。
2. **分母只算实际执行。** 环境阻断（`SYNC_FAILED`/SSH 不通/凭据失败）记 `blocked`，不写 `fail`；V20 全量 346 条中 11 条跳过单列，不混进失败率。
3. **证据链优先于模型自述。** 每条收益必须落到台账、报告、日志或 diff；只有推断、没有数据的标 `[INFERENCE]`。

## 2. P 类变更：流程组织

### 2.1 P1 建设期：从单人串行到 issue 分片并行

**变更前基线（2026-08 → 2026-09-28）**

| 时间 | 状态 |
|---|---|
| 2026-08 | 方案评审：对"免鉴权方案""1.1 新增检测项与修复工具"等设计材料做评审，结论拆成 issue 跟踪 |
| 2026-09-11 | 仓库起点（Initial commit） |
| 2026-09-28 | 12 条入口用例从 `test_mycase_0XX.py` 统一改名为 `PMS用例ID_用例标题.py`；补全局/入口 12 条、网络检测 19 条、系统完整性检测 12 条；在测试机 B 上验证 |
| 建设方式 | 人逐条写、逐条跑，无并发、无任务编号 |

**变更内容（2026-10-08 → 10-26）**

- 用例清单拆成任务编号（WS-1 ~ WS-461，会话中实际出现 305 个），2026-10-10 同日运行 461 个 Agent 会话；
- 每个 Agent 领一条用例，作业顺序固定：**确认 V20/V25 → 写脚本 → 双环境实跑 → 提交评审（不自动推送）**；
- 任务状态机：todo → in_progress → in_review → blocked/done，blocked 必须写"缺什么信息"；
- 每个会话跑在独立的工作区（导出数据显示 465 个会话使用独立 immutable 工作区），测试机侧加锁排队。

**代价**

- 77 个会话出现 `blocked` 状态变更；385 个会话命中"版本未确认"关键词（按文本计数，非逐条人工核验）——**这是最大的吞吐损失，且完全可预防**；
- 461 个会话同日并行、每个 issue 独立冷启动，输入 token 高达 5.3 亿，缓存读只占 6.4%，几乎全部按新输入计费；
- 并行任务共享工作区/分支/测试机，需要独立工作区 + 测试机加锁双保险。

**变更中暴露的 9 个问题（原建设期踩坑全量保留）**

| # | 现象 | 根因 | 解决 |
|---|---|---|---|
| 1 | 大量用例任务被置为 `blocked`，同批任务连环阻塞 | 用例清单只有 ID/标题/模块/优先级，没有 V20/V25 版本字段；作业规程要求"版本不明确必须暂停询问"，同批 4 个以上任务同时阻塞 | 承认这是**正确的门禁行为**，不是 Agent 偷懒；人在评论中一次性明确"V20、V25 都支持"，任务批量解除并补跑双环境。经验：批量任务开工前先把版本维度补进清单 |
| 2 | 用例在 V20 的虚拟显示（`:95`）上点击无反应、窗口被立即关闭 | ①AT-SPI 指针注入绑定在注册器自己的 display（`:0`），在 `:95` 上生成的鼠标事件实际点到 `:0`；②把应用挂到完整会话环境（`DISPLAY=:0`）会被窗口管理器立即关闭 | 读树与指针事件分离：读树跨 display 可用，指针注入必须同 display；非 `:0` 时改用 AT-SPI `Action.Press`（封装为 shim）；`manage.py` 增加 `TEST_DISPLAY` 贯穿执行链路；裸启动辅助与进程匹配同步加固。实测 V20 amd64（Xvfb `:95`）单条 27s、V25 loongarch64（默认 display）单条 51s |
| 3 | 同一用例在 V25 上"读不到文案" | V25 的 QML 节点向 AT-SPI 暴露的文本为空，但 `showing`/结构可用 | 断言改用 AT-SPI `showing` 状态 + 结构关系（按钮存在/汇总态图标切换/列表项出现）；确需文案时从产品 D-Bus/日志取 |
| 4 | 同一功能在 V20 与 V25 上判定不一致 | 架构从 amd64/Qt5 迁到 loongarch64/Qt6，控件树、依赖包、默认 display 行为都变 | 每条用例显式标注适用版本；不适合的版本用 `skipif` 并写明原因；双环境各跑一遍，差异写进 docstring，不写"两版都通过"的模糊断言 |
| 5 | 测试机 B 环境不稳定（超时、连不上、窗口不开） | 长跑、反复装包、图形会话被重置 | 执行前先做连通性与环境自检；失败先重试一次并记录；环境恢复后从断点继续；不把"环境没起来"算用例失败，也不静默跳过 |
| 6 | 并行任务互相踩工作区/分支 | 461 个会话同日运行，工作区、缓存、测试机都是共享资源 | 每个任务独立工作区（465 个会话使用独立 immutable 工作区）；提交走评审、不自动推送；测试机侧加锁，冲突时排队 |
| 7 | 用例命名与清单对不上，`-k` 选错对象 | 早期文件名是 `test_mycase_0XX.py`，与 PMS ID 无映射 | 迁移为 `PMS用例ID_用例标题.py`；csv、方法名、文件名三方一致性校验；改名后全量 `--collect-only` 验证唯一性 |
| 8 | 批量会话成本高、缓存几乎不复用 | 每个 issue 独立冷启动，输入 token 5.3 亿、缓存读只占 6.4% | 接受这是并行的代价；把公共上下文（版本规则、命名规范、环境说明）前置到任务模板，减少每个 Agent 的探索轮次 |
| 9 | 任务材料（用例清单/附件）拿不到或不完整 | 清单分散在 PMS 与附件里，Agent 需要先抓取再判断 | 先把清单固化成仓库内可读文件（csv/xlsx），任务里只给范围与 ID；抓取失败时记录缺失项，不猜 |

**建设期最重要的收益判断**：并行 Agent 的瓶颈不是写代码速度，而是"信息是否足够开工"。版本、环境、入口、命名四件事只要有一件含糊，N 个 Agent 就产生 N 次阻塞。把这些信息变成清单字段和任务模板，比换更强的模型有效得多——这也是第 2.3 节"人只定边界"的由来。

**变更前基线**：人工逐条执行、人工记录，无台账、无锁、无残留检查；用例失败后靠人翻日志判断是"用例错"还是"产品错"。

**变更中暴露的 8 个问题**

| # | 现象 | 根因 | 解决 |
|---|---|---|---|
| 1 | **忙等待空转**：64 个会话（30%）只领到 `busy` 就结束，每 5/10 分钟一次仍生成完整会话与被计费的 token | 固定节拍唤醒，不判断"有没有活" | 唤醒后先 `status`，busy 直接退出且不建长会话；把"有可用条目"作为触发条件（watch 台账而非固定节拍），或指数退避 |
| 2 | **环境阻断被记成用例失败**：35 个环境阻断会话中 21 条在测试机不可达时仍写 `fail` | 台账没有 `blocked` 终态，失败分支兜底写 `fail` | 台账增加 `blocked` 终态：`SYNC_FAILED`/SSH 不通/凭据失败只记 blocked；失败率分母只算实际执行过的条目 |
| 3 | **网络类用例切断自己的控制通道**：2005719 移走 `NetworkManager` 并重启，用例 PASS、回退返回 True，但测试机 04:12 起 IPv4 失联，后续 44 条阻断、21 条误判 | 破坏网络配置的用例跑在受控 SSH 通道上 | 网络破坏类禁止在受控 SSH 通道执行；用 netns/veth/独立网段；执行前后各做一次连通性断言；一旦断链先暂停定时任务再排障 |
| 4 | **并发 reclaim 双写覆盖**：08:00 监控与 08:05 另一次唤醒同时 reclaim 同一条，互相覆盖用例文件与 `my_app_widget.py` | 领取/回收没有版本基线 | reclaim 带 token 与 base 版本，写入前比对；文件级 owner；合并后强制 `py_compile` + 用例引用属性检查 + 重复 `def` 检查 |
| 5 | **心跳超时被误判为卡死**：owner 3,899s 无心跳，但远端可能仍在跑 5–13 分钟的音频修复 | 超时阈值按经验拍定，未按最长用例 | 先查远端进程与最新日志：有进程只延期、不抢占；远端无进程才 reclaim；阈值按最长用例设定 |
| 6 | **调度开销没人度量**：212 会话只有 68 个真正处理用例 | busy 比例、空转会话数、reclaim 冲突数未进入周报 | 把 busy 比例、空转会话数、reclaim 冲突数、鉴权失败数写进批次周报；调度器与用例代码同等对待 |
| 7 | **操作与记录不同步**：监控会话 08:06 记录后又被 08:13 覆盖，结论以谁为准不清 | `record` 允许改写 | `record` 只追加、不改写；以最后一条带证据的记录为准；冲突时保留两版并写明合并结果 |
| 8 | **编排者越权执行**：编排会话 6 轮、7 个工具错误，边汇总边想跑用例 | 编排角色职责未隔离 | 编排只做领取/汇总/决策，不执行用例；执行失败降级为人工，不在定时批次里现场改规程 |

**批次级收益判断**：无人值守的敌人不是模型能力，而是**环境状态机**——测试机在线、代码已同步、锁未过期、凭据有效，四者任一不成立，产出就是噪声。把"能不能开工"做成显式检查（开工四问），比让 AI 更努力地重试更有效。

| # | 现象 | 根因 | 处置 |

| 9 | 上下文爆掉后结论丢失（长会话 137 条指令后需重新解释） | 结论只存在会话里 | 关键结论即时写进笔记/台账；按"一条用例一次唤醒"控制上下文 |

## 3. E 类变更：工程资产

### 3.1 E1 一键部署：把测试环境的全部前提编码

**变更前基线**：每次换机、换版本都手工装包、手工排查 Qt/DTK 依赖、手工处理 polkit；出问题靠人回忆"上次怎么装的"。

**变更内容**：`deploy_pc_manager.sh` 不只是"装包"，而是把测试环境的全部前提写成可执行逻辑：

1. 按系统能力探测写 apt 源（V20/V25 不同源），备份后**保持生效**，隔离不匹配的源列表，避免构建期把基础库/SSH 服务连带升级；
2. 自动识别 V20（Qt5/DTK5）或 V25（Qt6/DTK6），处理开发包版本约束、DTK soname、`lrelease` 路径；
3. 从内部代码评审平台拉源码构建最新提交，**构建失败直接报错，不静默回退仓库旧版**；安装后校验版本与源码一致；
4. polkit 预授权（两套后端：pkla / rules_js），修策略文件权限，让 UI 自动化能跨过系统认证弹窗；
5. 安装用例依赖（`iputils-arping` 等）；
6. `.venv` 只装框架依赖，**不写系统 site-packages**；把 `.venv/bin` 前置到 PATH，`manage.py` 发现解释器不在 venv 时自动 `execv`；
7. V25 额外处理 PEP 668、`packaging` 无法卸载、`setuptools≥81` 移除 `pkg_resources`、`/usr` 只读 overlay。

**收益**

| 收益 | 证据 |
|---|---|
| 测的就是最新代码 | 构建失败直接报错，不静默回退旧版；安装后校验版本与源码一致 |
| 换机可复现 | 同一套脚本覆盖 V20 amd64 与 V25 loongarch64；版本与源码一致由脚本校验 |
| 自动化能跨过系统弹窗 | polkit 双后端预授权 + `pkcheck` 自检 |
| 不污染被测系统 | 框架依赖只进 `.venv`，避免 39 个同名 `.so` 与 apt 包冲突 |

**变更中暴露的 9 个问题**

| # | 现象 | 根因 | 解决 |
|---|---|---|---|
| 1 | 部署脚本报编译器依赖冲突，最终装成仓库旧版，用例覆盖不到新功能 | V20 的 Qt5/DTK5 运行时带签名后缀，仓库开发包要求精确同版本 | 编译器元包按 V20 基线降级（只降元包）；Qt5/DTK5/GL 开发包解包到 `/usr`，不注册 dpkg 依赖；按 V20 控制文件打包；构建后校验版本；**失败不静默回退** |
| 2 | 测试机装包后基础库/SSH 服务被升级，SSH 失联 | 机器混入另一版本源，构建期 `apt install` 连带升级 | 装包前按系统版本写源；隔离不匹配的源列表；备份到独立目录；部署期间保持源生效不还原 |
| 3 | V25 `pip` 报 `externally-managed-environment`；`pipenv` 装不上；`pytest-rerunfailures` 导入崩 | PEP 668；Debian 包无 RECORD；`setuptools≥81` 移除 `pkg_resources` | 能力探测而非版本号分支：pip≥23 加 `--break-system-packages`，统一加 `--ignore-installed`，固定 `setuptools<81`，剔除 apt 已提供的同名分发包；`/usr` 只读时 remount 可写 overlay |
| 4 | V25 检测项 D-Bus 报 `AccessDenied: Authorization denied` | V25 没有旧版 polkit 本地授权目录，预授权被静默跳过 | 双后端：目录探测 pkla / rules_js；写规则文件；`pkcheck` 自检；预授权放在产品安装后（action 安装后才注册）；`pkcheck -u` 不是"指定用户" |
| 5 | SSH 启动的电脑管家左侧栏毛玻璃消失、主题/图标漂移 | 裸 SSH 环境缺桌面/平台变量，DTK 不申请模糊区域 | `manage.py` 用 `setdefault` 补会话变量；按显示服务器类型决定是否强制 `QT_QPA_PLATFORM`；用窗口属性验证模糊区域存在 |
| 6 | 电脑管家报"关键库依赖问题"，被误判为用例没回退干净 | 测试项目把 numpy/Pillow/cryptography 等 39 个同名 `.so` 写进系统 site-packages，与 apt 包冲突 | 框架依赖只装 `.venv`；`.venv/bin` 前置 PATH；`manage.py` 自动 `execv`；部署同步依赖时剔除 apt 同名包 |
| 7 | 测试机无 `sshpass`、V25 无外网，apt/pip 全部失败 | 环境限制 | 宿主机起正向代理并写 apt 配置；用 paramiko/rsync/包装脚本替代 sshpass；部署脚本把代理作为可覆盖项 |
| 8 | Allure 套件列表中文乱码 | `conftest.py` 对 nodeid 做了双重 `unicode_escape` | 删掉两行转换；项目仓与 youqu-ai 框架仓同步修；重新构建 wheel（`dist/` 会残留旧 wheel） |
| 9 | 报告里单条用例优先级恒为 `normal` | 只用了 Allure 的 `L1–L4` 枚举，csv 里是 P1–P4 | `conftest.py` 增加 P1–P4 映射；重跑后 P1/P2 显示 blocker/critical |

**经验**：不要按 OS 大版本写 if/else，按**能力探测**（pip 版本、polkit 目录、`/usr` 是否 overlay、显示服务器类型）。版本号只用于报告标注与错误提示，不参与安装逻辑。V20/V25 分支越多，没机器验证的那一支腐烂得越快。

### 3.2 E2 依赖隔离：从系统 site-packages 到 `.venv`

| 项 | 变更前 | 变更后 |
|---|---|---|
| 框架依赖落点 | 系统 site-packages（39 个同名 `.so` 覆盖 apt 包） | 只装项目 `.venv`，部署时剔除 apt 同名包 |
| 入口解释器 | 依赖 shell 的 `python3`，可能绕过 venv | `.venv/bin` 前置 PATH，`manage.py` 检测到不在 venv 时自动 `execv` |
| 失败表现 | 产品报"关键库依赖问题"，被误判为用例回退不干净 | 该假故障消失，失败归因回到用例/产品本身 |

**边界**：手工执行 `python3 ...` 仍可能绕过 venv；入口必须统一走 `manage.py`，这也是"单入口"约束的另一半收益。

**变更中暴露的 8 个编排问题**

| # | 现象 | 根因 | 解决 |
|---|---|---|---|
| 1 | 同一台机器并发跑多个 `manage.py`，应用实例互相干扰 | 无全局锁 | 单入口（只用 `manage.py run`）；远端 `flock`；本地 owner 心跳；拿不到锁 `BUSY`/`SKIPPED`，不重试 |
| 2 | 网络类用例会切断 SSH，导致整批中断 | 破坏网络配置的用例与受控通道同宿 | 网络设置/IP 冲突类放到最后；用独立 netns/veth 构造；最终以隔离网段 + 串行为主 |
| 3 | 全量跑到一半测试机失联，远端进度与结果拿不到 | 无心跳与回收协议 | 心跳按最后心跳时间判超时；远端无进程才回收；恢复后以远端结果文件为准 |
| 4 | 报告/录屏持续累积，临时目录涨到 1.8G | 无保留策略 | 保留最近 30 份日志/结果、删 2 天前录屏与报告备份；磁盘低于阈值时监控介入 |
| 5 | 单条用例耗时差异巨大：检测类 100–350s，音频修复 5–13 分钟，失败重跑翻倍 | 统一超时拍定 | 用例级超时 1800s；失败上限 3 次（初次 + 2 次重试）；单条独立进程 + 独立日志；不做"边改边全量跑" |
| 6 | 全量结果没有按主题聚合，95 条失败无法排优先级 | 报告只给通过/失败 | 从日志提取断言行生成失败点清单，按清理/检测/修复/外设等主题分类；先修工程问题，再提产品缺陷 |
| 7 | 远端与本地代码漂移 | 手工上传、中文文件名 | 先改本地，再同步上传；中文文件名用 base64；远端不做直接编辑；跑前校验两端一致 |
| 8 | 用例执行被当成"应用启动次数" | 应用启动会自动触发检测任务 | 判断是否重跑看结果条数与执行计数，看完成回调时间线，不看启动次数 |

**经验**：长跑测试的第一公民是**串行与可恢复**，不是速度。台账 + 心跳 + 残留检查 + 报告裁剪，四件套缺一不可。

### 4.2 底层选型事实：不是运行时依赖，而是同源分叉

先厘清一个常见误解：本项目**不是运行时依赖** `youqu-ai` 仓库，而是 `youqu-startproject` 把框架源码复制进项目后本地使用。

| 对象 | 事实 | 判定方式 |
|---|---|---|
| `src/depends/dogtail/` | 与 youqu-ai 版本**逐字节一致** | `diff -rq` 无输出 |
| `src/dogtail_utils.py` | 与框架版不同，新增 222 行 / 删除 285 行 | `diff -u` |
| 运行时 import | 全部指向项目内 `src.depends.dogtail` / `src.dogtail_utils` | 用例 `from src.depends.dogtail.tree import root` |
| PO 基类 | `BaseWidget(Src)`，`Src.__init__` 组合 `DogtailUtils` | `src/__init__.py` |

所以准确说法是：**沿用 YouQu 的 dogtail 栈，库本体同源，封装层已本地分叉**。

PO（Page Object）在本项目的含义：用例只写业务语义（`widget.click_optimization_card_by_name("大文件清理")`），元素定位、等待/重试、业务动作集中在页面方法层（`my_app_widget.py`），347 个用例不出现 selector。选 AT-SPI/dogtail 作底层，是三层约束叠加的结果：

1. **Linux 桌面没有 Win32/UIA 的等价物。** Windows 有 UI Automation、macOS 有 AX，Linux 通用的结构化控件通道是 AT-SPI（无障碍总线）。Qt5/DTK5、Qt6/DTK6、QML 都会把控件树、role、name、状态发布到这条总线上——这是 PO 能"按名字找控件"的前提。
2. **PO 需要稳定寻址，不能靠像素。** 产品的 `objectName` / `accessibleName` 直接成为定位表达式（`$//optimization_startScanBtn`、`$//optimization_cardsView//大文件清理`）；表达式可 grep、可写日志、可在失败时区分"控件改名"与"页面没到"。
3. **dogtail 是最小可用封装。** 它提供 `root.application()` 建树、`GenericPredicate` 匹配、`findChildren` 递归、`Node.click()` 与搜索超时/重试，省去手写 pyatspi 递归。项目仍保留裸 `pyatspi` 做整桌面遍历（polkit 对话框判定），说明底层是同一条 AT-SPI 总线，dogtail 只是更薄的封装。

### 4.3 F1 诊断增强：`+222` 行的控件查找日志

**变更前基线**：查找失败只抛 `ElementNotFound`，无法区分元素名写错、页面没到、控件匿名、V20/V25 双写探测失败——过检期最常见的失败恰好是"找不到控件"。

| 新增 | 作用 |
|---|---|
| `_lookup_caller()` | 记录调用点 `文件:行号:函数`，未命中时直接跳到出问题的用例行 |
| `_lookup_log()` | 统一单行结构化日志：四态结果（直接命中 / 真实未命中 / 候选命中 / 候选未命中）、`expr`、`count`、`name/role/size`、`cost`、`caller` |
| `_lookup_tree_diag()` | 未命中时扫一遍 AT-SPI 树：目标 name 是否存在、匿名控件（未设 name）数量与角色分布/文本采样、遍历节点数、`difflib` 近似名（cutoff 0.6，最多 5 个） |
| `log_lookup_summary()` + `set_current_case()` | 会话结束按"表达式"和"用例"两个维度汇总未命中 |
| `probe` 参数 | 区分"多候选回退的探测未命中"（V20/V25 双写，属预期）与"真实未命中"，避免汇总误报 |

典型日志（单行，可 grep；`caller` 为占位）：

```text
[控件查找] 结果=真实未命中 hit=0 probe=0 expr=$//repair_runtimePage//开始修复
           count=0 cost=0.41s caller=<widget 文件>:<行>:<方法>
           目标name='开始修复' 同名控件=无 匿名控件=48 已命名控件=187
           匿名文本=[label]'磁盘工具' 遍历节点=331
```

**收益**

| 收益 | 证据 |
|---|---|
| 失败可定位 | 一行日志回答"元素名写错 / 页面没到 / 匿名控件 / 近似名"；63 条用例批量验证 |
| 汇总可量化 | 表达式维度 + 用例维度的未命中统计进入过检报告，可定位高频失效表达式 |
| 语义正确 | `probe` 未命中不计入"找不到控件"，V20/V25 双写不再污染失败归因 |

### 4.4 F2 精简兼容：`−285` 行去掉的默认行为

| 项目版差异 | 变更理由 | 收益 |
|---|---|---|
| 无 `require_visible=True` / `active_frame_only=True` 默认过滤 | 与 V20 QML `showing` 恒 False 的现实一致；可见性改由断言层 `_any_visible()`（`size != (0,0)`）判断 | 查找阶段不再全部假阴性；可见性判断只有一处 |
| 无 `find_elements_by_accessible_id()` / `find_element_by_accessible_id()` | 定位统一走 name 层级 | 减少多帧环境下的不确定性 |
| 无 `_node_matches_accessible_id()` / `_active_frame_extents()` / `_gi_find_descendants()` | 去掉 PyGObject 直接遍历 AT-SPI 判定活动帧的复杂路径 | 回到 dogtail 朴素递归，行为可预期 |
| 无 `config.actionDelay` 等 | 精简启动参数 | 少一类隐式等待 |

### 4.6 通道分工：AT-SPI 是操作通道，不是事实来源

**为什么其他通道只能辅助**（2026-11-18 对 347 个用例文件的实测）：

| 通道 | 使用规模（grep 计数） | 不能当主通道的原因 |
|---|---|---|
| AT-SPI / dogtail | 用例层 `self.dog.*` 169 次；widget 层 95 处 `find_element_by_attr` | 主通道：结构化、可按名寻址、状态可读 |
| 坐标 `ui.ini` + `ButtonCenter` | 用例层 `self.ui.` 仅 3 处 | 固定参考系 + `x,y,w,h`，动态列表、滚动、弹窗位置一变就失效 |
| `xdotool` 几何点击 | 46 个用例文件（13%） | 只用于 AT-SPI 拿不到或点不动的场景：`QTableView` 复选框由 delegate 绘制、自定义按钮 `Press` 不触发信号、V20 `:95` 虚拟显示的指针注入限制 |
| 图像识别 / OCR | 0 个用例 | 主题、DPI、毛玻璃、字体都会漂；只能证明"画面对"，读不到控件状态与层级 |
| 产品 D-Bus | 14 个用例文件 | 接口面只有系统 12 + 会话 13 个方法，覆盖不了全部 UI 行为；用于"单项结论拿不到"的取证与 `Fix` 类操作回退 |

由此形成实际的三层结构：**AT-SPI 负责操作，坐标/几何负责补洞，D-Bus/日志/X11 负责取证**。边界必须说清：AT-SPI 是操作通道，不是事实来源——"PASS 不是证据"（见 §5.1）。

**PO 的实现偏差**：标准做法是一页一个类，本项目是单个 `MyAppWidget`（26,226 行）。它保留了 PO 的核心收益（用例零 selector、定位变更只改一处），但丢了对象边界，代价是单文件耦合与并行修改冲突（公共层同一时刻只允许一个 owner，否则合并冲突会吞掉别人的改动）。

2. **技能即产品**：近 3 个月 `skills/` 的文件改动量是 `src/at` 的 6 倍以上，交付物重心从 Python API 转向"给 AI Agent 的 SKILL.md + 可执行脚本"。

## 5. Q 类变更：用例质量

### 5.1 Q1 判定口径：从"点到了"到"行为发生"

**变更前基线**：按钮点击成功即视为用例通过；断言只看 UI 元素存在，不看产品是否真的执行了动作。

| 变更 | 内容 |
|---|---|
| 行为断言 | 每个"点击后应发生某行为"的步骤都补行为断言：点击全面检测 → 检测运行态/结果态；点击修复 → 收到修复请求 + 修复窗口出现 |
| 分项隔离 | 点击目标分项卡片后，断言"该分项跑完且其它分项的已检查数为 0"，避免"实际跑的是全面检测" |
| 取证通道 | 产品日志 / D-Bus 返回 / 系统状态变化；AT-SPI 只证明"操作发出" |
| 有界等待 | 所有等待有超时、退出条件与现场信息；"看到就点 + 提前退出" |
| 跳过禁止 | 禁止 `pytest.skip` 逃避、`pass` 占位、只 `sleep` 不断言、`assert True` |

**收益**

| 收益 | 证据 |
|---|---|
| 失败可解释 | 15 条失败全部带日志/截图/行为证据：9 条产品缺陷、2 条功能下线、3 条判据与设计不符、1 条待复验 |
| 假绿消除 | 用例 PASS 但"用户看到没执行检测"这类问题被系统性拦住（V20 QML `showing` 恒 False 的场景见 §4.4） |
| 判据不被实现绑架 | 产品缺陷记 `fail` + 根因 + 证据；未改产品源码、未为迎合实现改判据 |

**代价**：单条耗时上升（检测类 100–350s，音频修复 5–13 分钟，失败重跑翻倍），因此必须有失败上限（3 次）与用例级超时（1800s）。

### 5.2 Q2 环境隔离与构造三原则

**变更前基线**：直接用测试机真实数据做清理/备份类用例；构造失败靠猜。

| 变更 | 内容 | 收益 |
|---|---|---|
| 真实数据隔离 | 前置把真实文件临时移出扫描范围，`finally` 按原路径恢复；重复文件用"尺寸 + 首尾采样"成组判定；候选超限直接报错，不静默部分隔离 | 清理类用例不再误删测试机真实数据 |
| 备份不覆盖 | 任何备份都不许无条件覆盖：发现遗留非空备份先恢复再重新备份 | 密钥环备份事故（真实文件永久丢失）后固化为规程 |
| 构造三原则 | 幂等（先清历史残留）、防御（写前解除 immutable）、顺序正确；构造失败时异常带计数、尾部日志、属性校验 | 系统级异常构造从"靠猜"变为可诊断 |
| 并发隔离 | 同族用例排查环境互踩；无法共存的改成 Skip；构造前先检查现状 | 用例 A 不再被用例 B 的构造覆盖而失败 |

### 5.3 Q3 命名与登记一致性

| 变更 | 变更前 | 变更后 | 收益 |

### 5.5 质量类其余坑（产品行为与 AT-SPI 边界）

已在 §4.3（控件查找）与 §4.4（可见性）讲过的两条不再重复，其余 15 条全量保留：

| # | 现象 | 根因 | 解决 |
|---|---|---|---|
| 1 | 单项检测结论读不到 | V20 QML 的 Label/ListView 不向 AT-SPI 暴露文本与单项状态，只有分项问题总数 | 走产品自身 D-Bus：检测任务 → 结果查询；会话总线不认识时回退系统总线；两条都不实现才退回分项级断言 |
| 2 | 用例停了很久，daemon 日志里却没有收到请求 | AT-SPI `Press` 被产品忽略（不是弹窗阻塞、不是鉴权失败） | 有界重试点击；点击后必须看到目标对话框/输出，否则重试而不是无限等 |
| 3 | 断言早过了，用例 400–500s 才结束，甚至被外层 timeout 杀掉 | 修复完成弹窗永不自动消失，`exec()` 一直阻塞 | 每轮看到弹窗就点，不依赖正文；命中关键字或修复窗口不可见即返回；统一收尾并在进程清理时兜底 |
| 4 | 弹窗断言写成"等正文出现再关" | DTK 标签的 AT-SPI `name` 是对象名，正文读不到 | 断言"弹框存在 + 标题 + 按钮文案"；正文从会话总线消息请求参数取；窗口关闭用 X11 标题判定（AT-SPI 节点销毁后仍报 `showing=True`） |
| 5 | 大文件/重复文件清理、启动管理器点击用例长期红 | 产品埋点用插件名比对页面 ID，实际值不匹配，统计全落到空间清理 | 产品缺陷单留档；按用户口径把通过条件收敛为"能进入运行时页并走到扫描/结果页/启动项列表加载"；埋点缺陷写进 docstring，不丢证据 |
| 6 | "一键修复需要鉴权"用例 120s 内无鉴权框，长期失败 | 产品对受信调用方免密修复 | 改判：10s 内无鉴权对话框 + 修复调用日志成功 + 修复结果计数正确；鉴权代理常驻，不能靠进程存在性判断 |
| 7 | CPU 温度/磁盘健康/jq 用例整组失败 | 测试机缺 `lm-sensors`/`smartctl`/`jq`；系统包白名单拒绝安装 | `ensure_package_installed(pkg, probe)`：已装复用，缺失则 apt 安装，失败先更新索引重试；安装前解析依赖闭包，临时写入白名单，`finally` 删除还原 |
| 8 | 要求"传感器缺失"的用例被另一条用例装上的依赖打断 | 依赖预检永久装包，而另一条把"缺失"写成死前置 | "要求缺失"的用例自己构造缺失态并回退（不卸载包、不改包管理状态）；"要求存在"的用预检补齐；同一台机器两个方向各自自洽 |
| 9 | 多分区显示用例突然失败，断言行数不符 | 测试机多了自动挂载的真实内部数据分区，产品列表把它也列出 | 改为"注入行必须出现且顺序正确 + 其余行必须是真实挂载点"；不写死行数；可移动盘被产品剔除，不能用挂载数反推 |
| 10 | 输入法"已激活"但按键直通、候选条永不出现 | 输入法与配套服务跨代配对，状态位仍报激活 | 清配套服务后整栈重启；重开编辑器并重试一次；恢复耗时不计入卡顿阈值；注入破坏验证恢复分支 |
| 11 | valgrind 用例 4–8 分钟且长期失败 | valgrind 在自身进程内运行被测程序，不 fork；计数命令输出被当子串判断；关窗常只回托盘；进程匹配先命中中间 shell | 只认 `valgrind.bin`；关窗 10s 不退发 SIGTERM，等泄漏汇总；判定按记录首帧归属（跳过包装帧），不按栈里是否出现产品帧；单轮从 318s 降到 74–79s |
| 12 | 进程相关判断偶发失效 | 进程名被截断到 15 字符（如 `deepin-pc-manag`） | 所有进程匹配改用截断名；排除列表同步补全 |
| 13 | 地址冲突检测在无冲突时也返回失败 | 同一 netns 内的 veth 对会把自己的广播回环回来 | 对端放进独立 netns；veth 用与办公网无关的网段，避免影响 SSH |
| 14 | 内存检测偶发"未判异常" | 两个实例相隔 8s 并发，共用同一 tmpfs，一个实例卸载掉另一个的挂载 | 用例加跨进程文件锁；拿不到锁直接 `SKIPPED`；内存构造余量 14%→10% |
| 15 | 磁盘 96% / `/boot` 93%，环境越跑越脏 | 填充文件在实例被中断后没进 `finally` | 杀残留实例 + 删除填充文件；查散落大文件；报告目录定期裁剪 |

**经验**：**PASS 不是行为发生的证据**。UI 自动化必须用"产品自己的日志 / D-Bus 返回 / 系统状态变化"取证；AT-SPI 只是操作通道，不是事实来源。

### 5.6 质量类剩余坑（判定与环境隔离）

| # | 坑 | 解决 |
|---|---|---|
| 1 | 判定只看"按钮点了"，不看行为 | 每个操作后补行为断言；点击全面检测 → 检测运行态/结果态；点击修复 → 收到修复请求 + 修复窗口出现 |
| 2 | 用例实际跑的是"全面检测"，却以为在测分项 | 点击目标分项卡片后，断言"该分项跑完且其它分项的已检查数为 0" |
| 3 | 清理类用例误删测试机真实数据 | 前置把真实文件临时移出扫描范围，`finally` 按原路径恢复；重复文件用"尺寸 + 首尾采样"成组判定；候选超限直接报错要求清理 |
| 4 | "智能选择→彻底删除"把结果列表所有组都删了 | 改为只删除选中的文件；断言删后剩余数量；环境隔离覆盖项目目录 |
| 5 | 密钥环备份把上一次有效备份覆盖，造成真实文件永久丢失 | 任何备份都不许无条件覆盖：发现遗留非空备份先恢复再重新备份；真实事故后写进规程 |
| 6 | 用例 A 被用例 B 的构造覆盖而失败 | 同族用例排查环境互踩；无法共存的改成 Skip；构造前先检查现状 |
| 7 | 构造系统级异常失败，排查靠猜 | 构造三原则：幂等、防御（写前解除 immutable）、顺序正确；异常带计数、尾部日志、属性校验 |
| 8 | 源列表残留 immutable，替换命令静默失败 | 构造与清理都先解除 immutable；写后校验属性并重试；产品侧同时报错误码 |
| 9 | coredump 前置偶发未落盘 | 写入后校验并重试 3 次；备份值异常时回落到系统默认值 |
| 10 | 用例编号撞号、跑错对象 | 登记表是唯一事实源；改完必须全过：csv 编号/ID 唯一、每个方法在 csv 有登记、编号等于文件名前缀、`--collect-only` 唯一且挂对文件 |
| 11 | 同一用例被重复收集、一个文件两条用例 | 修收集逻辑；承认"一个文件多条用例"是登记表允许的，跑全量时单独拆开验证 |
| 12 | 用例里日志调用静默无输出（`log` 是类装饰器，传字符串时 `getmembers` 空迭代、`return cls` 原样返回被丢弃，静默不报错） | 区分 `@log` 装饰器与函数式调用，逐文件替换为 `logger.info()`；**2026-11-18 实测仍余 24 个用例文件 100 处 + `widget/my_app_widget.py` 6 处 = 106 处未改**，属部分修复 |
| 13 | 100MB 大文件正好卡在产品"大于 100MB"阈值 | 测试数据提到 120MB；阈值类用例显式写出边界，并用 100/101/120MB 验证 |

**经验**：判定口径要"等价但可证"：允许页面/元素/进程/返回码/文件变化等等价断言，但禁止常量断言、空跑、只等不断言。破坏性用例先隔离真实数据，备份永不覆盖，收尾必须自查。

**四个成本结论**

1. **主力都是 flash 级模型**，不是最贵的推理模型。任务绝大多数是"读日志 → 定位 → 改一个文件 → 跑一条用例"，吞吐与工具调用稳定性比单次推理深度更重要。212 个定时会话全部由 `deepseek-v4.1-flash-1017` 完成。
2. **任务形态决定模型选择**：建设期"短任务、海量并行"用 `deepseek-v4-flash`；过检交互"长会话、重工具链"用 `deepseek-v4.1-flash-1017`；无人值守"单轮、强规程"同一模型每会话 1 轮；架构分析"一次读 40k 行源码"用 `gpt-5.6-sol` 处理 9.0M 输入。
3. **缓存复用率是成本分水岭**：过检交互 95.7%（1.74B / 1.82B），无人值守 96.2%（268.5M / 279.1M），建设期只有 6.4%（36.7M / 573M），三条线合计 76.6%（2.05B / 2.67B）。建设期 461 个会话同日并行、每个 issue 独立冷启动，输入 token 5.3 亿，几乎全部按新输入计费。
4. **模型切换有成本**：同一会话跨模型会丢上下文风格；后期统一主力模型后，文档与台账格式才稳定。

## 8. 可复用清单（按变更类别）

### 8.1 硬约束速查（一句话，细节见 8.2–8.6）

1. 能力探测优于版本判断。
2. 构建失败不静默回退。
3. PASS 不是证据，日志/D-Bus/系统状态才是。
4. 有界重试 + 提前退出。
5. 构造-执行-断言-回退四段闭环，`finally` 是硬约束。
6. 负面状态自己构造，不依赖机器现状。
7. 单一事实源：编号、优先级、期望以登记表为准。
8. 单入口串行：一把锁、一个入口、一条用例。
9. 证据链即交付物：台账、日志、复跑次数。
10. 文档是 AI 的接口：实测笔记写给下一位接手者。
11. 环境故障与用例失败分账，`blocked` 独立终态。
12. 调度器也是被测对象：busy、空转、reclaim 冲突都要度量。

### 8.2 P 类可复用：流程与组织

| # | 做法 | 收益证据 | 落地方式 |
